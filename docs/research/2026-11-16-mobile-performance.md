- 游戏页 `main` 最小高度从 70vh 改为 100vh，页脚在加载时就在首屏以下，不再跳动。
- 根布局声明 `icon: /icon.svg`，浏览器不再请求不存在的 `/favicon.ico`。

### LCP 审计为什么不带 DOM 节点详情

已观察到的：

- **LCP 记录指向第一个横幅节点。** 用 `PerformanceObserver` 记录 LCP（实际限速 2 次、不限速 1 次）。每次都只有一条记录，元素是页面上出现的第一个横幅节点，也就是静态 HTML 里那个。限速时记录时间为 1,768、1,808 ms，与 Lighthouse 的 1,763、1,790 ms 接近。
- **这个节点在加载中被换掉。** 一次加载共创建 4 个横幅节点，依次为：
  1. 静态 HTML（`page.tsx` 的 `GameLoading` 占位）；
  2. 水合时重新渲染的同一占位；
  3. 游戏客户端载入后的加载画面；
  4. 就绪后的选角画面。

  加载结束时文档里只剩最后一个，LCP 记录的那个节点已不在文档里。三次运行都没有记录到后续节点的 LCP 条目。
- **水合时 `div.game` 整个被替换。** 有三点相互印证，判断是水合时丢弃了静态内容、在客户端重新渲染：
  - 静态 HTML 里这个 `Suspense` 边界带 `<!--$!-->` 标记，表示该边界转为客户端渲染；
  - `page.tsx` 用 `next/dynamic` 的 `ssr: false` 载入游戏客户端；
  - 容器替换日志显示 `div.game` 在水合时被替换。
- **Lighthouse 取详情的方式。** Lighthouse 13.6.0 在加载结束后用 `DOM.resolveNode`，按 trace 里的节点编号取节点详情，找不到节点时直接省略（`core/gather/gatherers/trace-elements.js`、`core/gather/driver/dom.js`）。
  - 临时脚本里，已移除的第一个横幅节点在回收前仍能取到（`isConnected` 为 false）。
  - 强制垃圾回收后报 `No node with given id found`（各 2 次）。
- **对照组。** cd1246b、15058ef 两批共 10 份报告，两项审计都没有节点详情。59f2849 的 3 份都有，列的是选角画面里的横幅。那时游戏页的加载占位只有一行文字，横幅只在选角画面渲染一次，一直留在文档里。

推断的：

- Lighthouse 不强制回收。10 次都缺详情，推断节点在 Lighthouse 取详情前已被回收。这一步没有在 Lighthouse 内部直接观察到。（2026-11-19 已实测，见"两处推断的实测"一节。）

处理：15058ef 这批 5 次测量 CLS 都是 0，没有记录到布局位移；目前的证据只涉及诊断详情缺失，所以暂不为此调整结构。可行方案之一是把欢迎区移到 `next/dynamic` 边界外，由页面控制何时隐藏。

## 两处推断的实测（2026-11-19）

上一节有三处标为推断。这次在正式站上直接测了：

- 版本 7d3d0ce。它与 15058ef 之间只改了文档，页面代码相同。
- 工具是同一个 Lighthouse 13.6.0，经 Puppeteer 页面运行，其余为默认手机配置。
- 测量用的临时脚本不提交。

### Lighthouse 取不到 LCP 节点：内部调用失败，保留引用后能取到

- **记录内部调用。** 包装 Puppeteer 的 CDP 会话，记录 Lighthouse 内部每次 `DOM.resolveNode` 的节点编号和返回。
- **对照组。** 不加任何页面脚本，共 6 次：模拟限速 3 次、实际限速 3 次。
  - 每次 trace 里最后一个 LCP 候选都是图片节点。
  - Lighthouse 按这个编号调用 `DOM.resolveNode`，6 次都返回 `No node with given id found`。
  - 两项 LCP 审计都没有节点详情。
- **保留引用组。** 用 `evaluateOnNewDocument` 注入脚本，在数组里保留每个横幅节点的引用，模拟限速 2 次。
  - 同一调用 2 次都成功。
  - 两项 LCP 审计都列出了节点详情，元素是 `div.townBanner`。
  - 它的位置矩形全为 0，路径只到 `section` 为止，说明它已脱离文档，是被换掉的那个横幅。
- **结论。** 已观察到的有两点：Lighthouse 内部取这个节点失败；页面持有引用时能取到。再结合上一节的强制回收实验，有力支持"已移除、无引用的节点在取详情前被回收"这一解释。具体的回收事件和时点没有观察到，仍属推断。

### 同批请求分带宽：横幅变慢、样式表晚到

实际限速，分两批交替运行。第一批：正常与屏蔽横幅各 3 次。第二批：正常与屏蔽脚本各 2 次。屏蔽的是首批 10 个脚本中的 9 个 Next.js 包（`/_next/static/chunks/*.js`，约 169 KiB）；Cloudflare 统计脚本 `beacon.min.js`（约 10 KiB）照常加载。屏蔽都用 Lighthouse 的 `blockedUrlPatterns`。时间从 HTML 请求开始计：

| 游戏页 | 样式表 | 横幅 | FCP |
|---|---|---|---|
| 正常（第一批 3 次） | 624–654 → 1,700–1,732 ms | 622–652 → 1,581–1,613 ms | 1,748–1,786 ms |
| 屏蔽横幅（3 次） | 618–656 → 1,657–1,665 ms | — | 1,700–1,711 ms |
| 正常（第二批 2 次） | 624–643 → 1,696–1,725 ms | 622–641 → 1,601–1,642 ms | 1,747–1,773 ms |
| 屏蔽 9 个 Next.js 包（2 次） | 635–642 → 1,365–1,370 ms | 633–640 → 1,337–1,339 ms | 1,413–1,427 ms |

- **横幅变慢来自与脚本分带宽。** 屏蔽这 9 个包后，横幅约 0.70 s 下完；正常时约 1.0 s，改动前约 0.65 s。

### 代价

- **HTML 变大。** 游戏页 HTML 传输 3.4 → 14.1 KiB，首页 5 → 15 KiB。
- **游戏页仍会再下一次样式表。** 约 2.4 s 时游戏客户端的动态包载入，又按链接请求了同一份样式表，10.1 KiB。三次的总传输 508 → 554–560 KiB。重复下载和预取在正式站的实际成本，以上线后的测量为准。
- **跨页不再共用缓存。** 样式表不再作为单独文件被各页共用缓存。客户端跳转与预取的载荷也带上了 CSS。
- **离线缓存。** Service worker 安装时缓存 6 个页面。每页 HTML 原始约多 130 KB，brotli 压缩后约多 11 KB；浏览器缓存的实际占用没测。
  - 内联后，`/result`、`/whatif` 的 `<style data-href>` 里有两个用空格隔开的路径。原来的正则把它当成一个地址交给 `cache.addAll`，安装整体失败（审核发现）。
  - 已改 `sw.js`：只提取不含空白的单个地址。
  - 新增 e2e 用例：等 service worker 接管页面后断网，`/result`、`/whatif`、`/policy` 都能打开。这条用例在未修复的构建上失败，修复后通过。
- **实验性开关。** `inlineCss` 仍是 Next 的实验性选项。

## 没做的（建议）

- 中英文两套界面词典（约 68 KB）每页都一起加载；规则引擎与政策数据（约 280 KB 原始）首页也加载（首页"政策核对截至"只用到其中的日期）。网站页性能分已在 96 以上，收益有限，暂不处理。
- 游戏页在游戏客户端载入时会再按链接下载一次已内联的样式表（约 10 KiB，见"内联 CSS"一节），不在首次绘制和 LCP 之前，暂不处理。
